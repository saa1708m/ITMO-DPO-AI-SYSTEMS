## 3. Методические указания по выполнению и оцениванию заданий

### 3.1. Общая характеристика заданий

Задания модуля предназначены для текущего контроля по темам, связанным с жизненным циклом ML-систем, ролями участников AI/ML-проектов и основами архитектуры ML-платформ. Модуль формирует стартовое системное представление о том, как из исследовательского прототипа возникает промышленное решение и какие компоненты необходимы для его разработки, поставки и сопровождения.[page:2]

Тестовые задания используются для быстрой проверки понимания ключевых понятий и терминов. Лабораторные работы и кейс позволяют оценить способность обучающегося применять архитектурное мышление к учебным и приближённым к практическим сценариям.[page:2]

### 3.2. Методические указания для студента

Перед выполнением заданий рекомендуется изучить лекционные материалы по следующим вопросам:

- жизненный цикл ML-системы и его этапы;
- отличие исследовательского прототипа от промышленного ML-решения;
- роли ML Engineer, MLOps Engineer и смежных участников команды;
- основные компоненты ML-платформы: хранение данных, обучение, реестр моделей, deployment, serving, мониторинг;
- базовые архитектурные паттерны ML-сервисов.

При выполнении лабораторной работы 1.1 рекомендуется сосредоточиться на выделении этапов жизненного цикла, ролей и ключевых компонентов рассматриваемого ML-продукта. При выполнении лабораторной работы 1.2 следует сначала подготовить архитектурную схему, затем описать компоненты стенда и только после этого реализовывать конфигурацию запуска.[page:2]

В кейсе важно не просто перечислить технологии, а показать, как связаны между собой элементы системы, какие функции они выполняют и какие ограничения или риски видны уже на уровне базовой архитектуры.[page:2]

### 3.3. Методические указания для преподавателя

Тесты целесообразно использовать после завершения каждой темы модуля как средство оперативной проверки терминологии и базового понимания архитектуры ML-систем. Лабораторные работы и кейс рекомендуется оценивать не только по полноте ответа, но и по способности обучающегося объяснить, почему система устроена именно так.[page:2]

При проверке необходимо учитывать, что модуль 1 соответствует уровню `Б` по индикатору `LC-3.1`, поэтому основное внимание должно уделяться корректности выделения компонентов, пониманию их ролей и логике связей между ними, а не глубокой проработке production-ready реализации.[page:1][page:2]

## 5. Система оценивания

### 5.1. Оценивание тестов

Каждый тест предназначен для проверки базового понимания ключевых понятий модуля. Рекомендуется использовать шкалу, при которой каждый правильный ответ оценивается в 1 балл, а максимальный балл определяется количеством вопросов в тесте.[page:2]

Пример рекомендуемой шкалы для теста из 10 вопросов:

| Количество правильных ответов | Баллы | Рекомендуемая оценка |
|------------------------------|-------|----------------------|
| 9–10 | 9–10 | Отлично |
| 7–8 | 7–8 | Хорошо |
| 5–6 | 5–6 | Удовлетворительно |
| 0–4 | 0–4 | Неудовлетворительно |

Минимальным результатом, подтверждающим освоение темы, рекомендуется считать не менее 60 % верных ответов.[page:2]

### 5.2. Оценивание лабораторных работ и кейса

Для лабораторных работ и кейса рекомендуется использовать 10-балльную рубрику на основе пяти критериев по 0–2 балла:

| Критерий | 0 баллов | 1 балл | 2 балла |
|----------|----------|--------|---------|
| Корректность содержания | Содержание задания не раскрыто | Раскрыто частично | Задание раскрыто полно и корректно |
| Выделение компонентов и связей | Компоненты не выделены или выделены ошибочно | Выделены частично | Компоненты и связи выделены корректно |
| Архитектурная логика | Логика решения отсутствует | Логика описана частично | Архитектура описана последовательно и обоснованно |
| Качество оформления | Структура и оформление слабые | Оформление частично соответствует требованиям | Работа структурирована и аккуратно оформлена |
| Защита и объяснение решения | Обучающийся не может объяснить работу | Объяснение частично уверенное | Объяснение полное, логичное и осмысленное |

Итоговый балл определяется суммой по критериям. Для кейса рекомендуется делать больший акцент на качестве архитектурного анализа и способности объяснить ограничения выбранного решения.[page:2]

## 6. Рекомендации по проведению контроля

Перед началом контроля преподавателю рекомендуется заранее сообщить формат задания, критерии оценивания, допустимые источники и правила использования внешних инструментов. После проверки тестов полезно разбирать типовые ошибки: путаницу между ролями, смешение компонентов платформы и непонимание различий между этапами жизненного цикла и техническими сервисами.[page:2]

При защите лабораторных работ и кейса рекомендуется задавать короткие уточняющие вопросы по архитектуре, ролям компонентов и их взаимодействию. Это помогает проверить самостоятельность выполнения и глубину понимания материала.[page:2]

Эти результаты служат основой для последующих модулей, связанных с данными, экспериментами, контейнеризацией, развёртыванием и мониторингом.[page:1][page:2]
