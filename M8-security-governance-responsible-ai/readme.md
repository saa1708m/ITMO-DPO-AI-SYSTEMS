## 1. Описание модуля

| Параметр | Содержание |
|----------|------------|
| **Название модуля** | Безопасность, governance и ответственный ИИ |
| **Раздел РПД** | Модуль 8. Безопасность, governance и ответственный ИИ |
| **Темы** | 8.1. Безопасность ML-платформ и governance моделей. 8.2. Ответственный ИИ и устойчивость моделей. |

## 3. Методические указания по выполнению и оцениванию заданий

### 3.1. Общая характеристика заданий

Оценочные средства модуля направлены на проверку способности обучающегося применять инженерные практики безопасности, governance и ответственного ИИ при сопровождении ML-систем в рабочей версии программного обеспечения.

Тестовые задания предназначены для текущего контроля по завершении соответствующего лекционного или практического занятия модуля 8 дисциплины «Безопасность, governance и ответственный ИИ». Они позволяют проверить степень освоения понятий и инструментов, связанных с безопасностью ML-платформ, управлением секретами, RBAC, аудитом моделей, документацией model cards и datasheets, анализом bias, fairness и устойчивости моделей.

Тест может выполняться:

- в конце лекционного или практического занятия;
- в качестве самостоятельной домашней работы;
- в электронной образовательной среде;
- в рамках подготовки к рубежному контролю и промежуточной аттестации.

Рекомендуемое время выполнения одного теста составляет 10–20 минут.

Каждый тест содержит 10 заданий. К каждому заданию предлагается 5 вариантов ответа. В каждом задании имеется только один правильный ответ.

Задания имеют преимущественно прикладной и инженерный характер. Они проверяют не только знание терминов, но и понимание того, как безопасно хранить и использовать секреты, как настраивать минимально необходимые привилегии, зачем нужны model cards и datasheets, как проводится аудит модели, как рассчитываются fairness-метрики и почему объяснимость важна для governance ML-систем.

Лабораторные работы проверяют способность обучающегося:

- настраивать централизованное хранение секретов в HashiCorp Vault;
- использовать GitHub Secrets в CI/CD-пайплайне;
- не допускать публикации секретов в репозитории и логах;
- настраивать Vault policies для разных ролей;
- реализовывать разграничение доступов через Kubernetes RBAC;
- проверять положительные и отрицательные сценарии доступа;
- анализировать риски использования секретов и токенов;
- выбирать датасет с sensitive attributes;
- обучать baseline-модель;
- рассчитывать стандартные метрики качества;
- выполнять групповой анализ качества модели;
- рассчитывать fairness-метрики с помощью Fairlearn и/или AIF360;
- анализировать причины bias;
- применять методы mitigation bias;
- готовить Model Card и отчёт об аудите модели.

### 3.2. Методические указания для студента

Перед выполнением заданий рекомендуется повторить:

- что такое secret management;
- почему секреты нельзя хранить в Git-репозитории;
- назначение HashiCorp Vault и GitHub Secrets;
- различия между статическими и динамическими секретами;
- принцип минимально необходимых привилегий;
- назначение RBAC;
- назначение Kubernetes `ServiceAccount`, `Role`, `ClusterRole`, `RoleBinding`, `ClusterRoleBinding`;
- способы проверки доступов через `kubectl auth can-i`;
- назначение model card;
- назначение datasheets for datasets;
- понятия audit trail, approvals, lineage и governance;
- понятия bias, fairness, sensitive attribute, privileged group, unprivileged group;
- fairness-метрики: selection rate, demographic parity, equalized odds, equal opportunity, FPR/FNR difference;
- инструменты Fairlearn и AIF360;
- базовые методы mitigation bias;
- назначение SHAP и LIME;
- понятие adversarial attacks;
- роль ГОСТ Р 71476-2024 как терминологической и концептуальной основы для описания ИИ-систем.

При выполнении лабораторной работы 8.1 важно показать не только создание секретов, но и корректную модель разграничения доступов:

- секреты не должны храниться в коде;
- реальные production-секреты использовать запрещено;
- значения секретов не должны выводиться в логи GitHub Actions;
- каждая роль должна иметь только необходимые права;
- сервис инференса не должен иметь доступ к секретам обучения и базе данных;
- CI/CD не должен иметь права `cluster-admin`;
- должны быть проверены как разрешённые, так и запрещённые действия;
- в отчёте должны быть описаны риски и меры повышения безопасности.

При выполнении лабораторной работы 8.2 важно показать полный цикл аудита модели:

- обосновать выбор датасета и sensitive attribute;
- выполнить EDA и анализ распределений по группам;
- обучить baseline-модель;
- рассчитать общие метрики качества;
- рассчитать метрики по группам;
- рассчитать fairness-метрики;
- интерпретировать результаты;
- применить минимум один метод mitigation bias;
- сравнить модель до и после mitigation;
- подготовить Model Card;
- сформулировать ограничения, риски и рекомендации по использованию модели.

Использование готовых решений, чужих ответов и автоматических средств генерации ответов без самостоятельного анализа задания не допускается.

## 5. Система оценивания

### 5.1. Оценивание тестов

Каждый тест предназначен для проверки понимания безопасности ML-платформ, governance моделей, ответственного ИИ, fairness, bias, устойчивости моделей и инструментов аудита.

Каждый тест содержит 10 заданий. Каждый правильный ответ оценивается в 1 балл. Максимальная оценка за тест — 10 баллов.

| Количество правильных ответов | Баллы | Рекомендуемая оценка |
|------------------------------|-------|----------------------|
| 9–10 | 9–10 | Отлично |
| 7–8 | 7–8 | Хорошо |
| 5–6 | 5–6 | Удовлетворительно |
| 0–4 | 0–4 | Неудовлетворительно |

Минимальным результатом, подтверждающим освоение темы, рекомендуется считать не менее 60 % правильных ответов, то есть 6 правильных ответов из 10.

При использовании рейтинговой системы результат может быть переведён в проценты по формуле:

\[
P=\frac{N_{\text{правильных ответов}}}{N_{\text{заданий}}}\cdot100\%.
\]

- количество заданий;
- время выполнения;

- порядок выбора и фиксации ответов;
- критерии оценивания;
- срок и способ предоставления работы.

Если тест выполняется в качестве домашнего задания, рекомендуется установить конкретный срок сдачи. При необходимости можно просить студентов сохранять краткие промежуточные рассуждения по вопросам безопасности, разграничения доступов, governance-процедур, fairness-анализа или выбора mitigation-подходов.

После проверки целесообразно провести краткий разбор заданий, вызвавших наибольшие затруднения. При анализе результатов рекомендуется обращать внимание не только на итоговый балл, но и на характер ошибок.

Если значительная часть группы допустила одну и ту же ошибку, соответствующий вопрос рекомендуется повторно разобрать на следующем занятии.

- почему нельзя хранить секреты в Git;

- зачем нужен Vault;
- какие риски есть у долгоживущего `VAULT_TOKEN`;
- чем GitHub OIDC безопаснее статического токена;
- что такое принцип минимально необходимых привилегий;
- почему CI/CD не должен иметь `cluster-admin`;
- как проверить доступы через `kubectl auth can-i`;
- почему важны отрицательные проверки доступа;
- какие риски остаются в предложенной архитектуре.

- какой mitigation-подход был применён;
- как изменились quality- и fairness-метрики после mitigation;
- какие ограничения и запрещённые сценарии использования указаны в Model Card.

## 7. Назначение результатов контроля

Результаты контроля по модулю 8 показывают, способен ли обучающийся применять практики безопасности, governance и ответственного ИИ при промышленной эксплуатации ML-систем.

По итогам модуля обучающийся должен уметь:

- объяснять назначение secret management в ML-платформах;
- безопасно использовать HashiCorp Vault и GitHub Secrets;
- не допускать хранения секретов в Git-репозитории;
- настраивать Vault policies для разных ролей;
- применять принцип минимально необходимых привилегий;
- настраивать Kubernetes RBAC;
- проверять разрешённые и запрещённые сценарии доступа;
- анализировать риски CI/CD и production-секретов;
- объяснять назначение model cards и datasheets;
- проводить базовый аудит ML-модели;
- выбирать sensitive attributes для fairness-анализа;
- рассчитывать метрики качества по группам;
- рассчитывать fairness-метрики;
- интерпретировать bias и возможные причины его возникновения;
- применять методы mitigation bias;
- готовить Model Card;
- формулировать ограничения, риски, рекомендации и запрещённые сценарии использования модели.

Эти результаты являются основой для дальнейшей работы с production-ready MLOps-практиками: безопасным управлением доступами, аудитом моделей, трассируемостью данных и артефактов, мониторингом fairness, контролем drift, объяснимостью предсказаний и ответственным внедрением ИИ-систем.
